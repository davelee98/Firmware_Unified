# Plan — nRF51822/S130 slim OpenDisplay target for GreenTags LT213A

Date: 2026-09-06
Status: SOFTWARE IMPLEMENTED — host, corpus and cross-build gates pass; every hardware gate remains open.
Baseline: Firmware_Unified `184c302`.
New target: `targets/nrf51-s130/`, initially **only** GreenTags LT213A, nRF51822
128 KiB Flash / 16 KiB RAM, 104 × 212 monochrome panel.
Hardware/reference implementation:
[`shirok1/greentags-lt213a-opendisplay`](https://github.com/shirok1/greentags-lt213a-opendisplay)
at `28df8b6ce1506b82665809763dc92180b616e916`.
Other references: live `../Firmware_NRF` at
`71b870c12855b2bab4db11fdf1fb213818f3f3a8` for Nordic SDK/S130 integration patterns,
`../opendisplay-protocol` for the canonical wire contract, and `../py-opendisplay` for actual host
behaviour. The sibling repositories remain read-only.

## Outcome

Add a deliberately small, plaintext-only OpenDisplay firmware for an nRF51822 tag whose fixed
ATT MTU is 23 (20-byte ATT values). The first shippable image does one useful job reliably:

1. advertise and accept one BLE peripheral connection;
2. expose enough read-only identity/configuration for an unmodified `py-opendisplay` client to
   discover 104 × 212 monochrome capabilities;
3. receive a full uncompressed image through `DIRECT_WRITE` without a framebuffer;
4. refresh the LT213A panel and report success or timeout;
5. recover safely from malformed input, disconnects, incomplete transfers and panel faults.

The target does **not** attempt feature parity with ESP32, nRF52/nRF54 or BG22. It does not compile
the shared session/dispatch/transfer composition: the S130 reservation leaves only 18 KiB of
application Flash and 8.25 KiB of application RAM, and that composition assumes a 244-byte BLE
frame and response queue. This target is an explicit constrained-profile exception, kept narrow by
its own command matrix, corpus profile and size/symbol gates.

The linked reference establishes feasibility on this exact part and panel: it directly drives S130
2.0.1 from C, reserves 18,432 B application Flash and 8,448 B application RAM, handles ATT queued
writes, and streams the panel without a framebuffer. It also implements authentication, PIPE,
compression, writable config and an `FD 46` response envelope. Those features are evidence, not the
scope to copy: this plan deliberately omits them and imports only the verified monochrome panel
sequence plus narrowly useful S130 transport behaviour.

The audit also identifies behaviours that need regression tests rather than reuse. The legacy S130
GATT path dispatches only `BLE_GATTS_EVT_WRITE` with a 20-byte maximum attribute, so it does not
solve long OpenDisplay requests. Its direct-write flow must not be allowed to ACK a zero-length or
overflowing DATA frame, accept END while idle, ACK END before confirming exactly 2,756 bytes, or
silently retain state across disconnect. The new target specifies each case independently below.

## Decisions fixed by this plan

### 1. No application authentication or encryption

- Do not compile `od_session`, `od_gate`, a crypto HAL, AES-CCM/CMAC, nonce state, replay state or
  key storage.
- Do not enable BLE pairing, bonding or a security database. The GATT characteristic is open.
- The static configuration contains no `SecurityConfig` TLV and the advertisement encryption bit
  is always clear.
- `CMD_AUTHENTICATE` is recognized and returns the canonical three-byte
  `[0x00, 0x50, AUTH_STATUS_NOT_CONFIG]` response. It never returns a challenge.
- This is an intentionally unauthenticated product: any nearby connected peer can replace the
  image. Remote config writes, DFU, power control and reboot are excluded so the open surface is
  limited to display content and read-only discovery.
- Release notes must state the absence of access control. It must never be described as secure
  because the radio link happens to be BLE.

### 2. Keep the ordinary OpenDisplay wire format

Do not introduce a `slim` opcode namespace or copy the reference project's `FD 46` long-response
envelope in the first implementation.

The ATT MTU limit can be satisfied without it:

- ordinary replies, ACKs, NACKs, PIPE refusals and refresh status are at most 20 bytes;
- `FIRMWARE_VERSION` uses an 8-character SHA, so its response is 14 bytes including patch;
- `READ_MSD` is 18 bytes;
- `CONFIG_READ` already permits one or more notifications. Emit a maximum 20-byte frame: 14 data
  bytes in chunk 0 and 16 in later chunks;
- requests longer than 20 bytes use standard ATT Prepare/Execute Write into one bounded S130 user
  memory block. This is BLE transport segmentation, not a new OpenDisplay wire protocol;
- expose only GATT Write Request + Notify, not Write Without Response. That makes current Bleak
  use the reliable long-write path for 0x71 frames instead of attempting a 232-byte Write Command.

Gate 0 must prove Prepare/Execute behaviour on every required host platform before the protocol
engine is built around it. If a required client cannot issue long writes, the fallback is a host
transport ceiling of 20 and 18-byte `DIRECT_WRITE_DATA` payloads. Only if that also proves
unworkable may a custom fragmentation envelope be reconsidered. Authentication's 23-byte
challenge is not a reason to add one because this target never emits that challenge.

### 3. Static, read-only configuration

- Define a target-local `OD_NRF51_STATIC_CONFIG_MAX_SIZE=1024u` consumed by the generated config
  source and its artifact test. Do not override shared `OD_CONFIG_MAX_SIZE`: only
  `od_config_asm`/`od_config_store` consume it, neither source is compiled here, and introducing an
  inert value would create a needless third shared ABI composition.
- Build one canonical 133-byte expected TLV config in Flash: System,
  Manufacturer, Power and Display only.
- The display row is fixed to `OD_PANEL_IC_EP213_104X212`, 104 × 212,
  `OD_COLOR_SCHEME_MONO`, the verified rotation, and `DIRECT_WRITE` as its only transmission mode.
- No ZIP, streaming decompression, PIPE, partial, NFC, LED, buzzer, touch, sensors, LAN or WiFi
  capability bit may be advertised.
- `CONFIG_READ` streams that Flash blob in standard <=20-byte response frames without first
  copying it to RAM.
- `CONFIG_WRITE`, `CONFIG_CHUNK` and `CONFIG_CLEAR` return their canonical unsupported/NACK
  disposition and never touch Flash.
- Generate the blob deterministically from a target board description, check the generated bytes
  in, static-assert its size is <=1,024 bytes, and validate it with the shared host-side config
  parser without a special shared-library build. The firmware does not carry a TLV parser or
  config assembly buffer. Because the configuration is immutable, the 1 KiB target-local cap does
  not create a remotely discoverable write limit: all config writes are refused before size
  matters.
- Until `../opendisplay-protocol` assigns an nRF51822 `OpenDisplayICType`, use the protocol-approved
  unknown value (`0xFFFF`) as the reference implementation does. Never impersonate nRF52811 or
  nRF52840. Adding a real enum is external follow-up work, followed by the normal header sync.

### 4. One panel and one transfer path

- Only the LT213A 104 × 212 monochrome OTP/full-refresh path is in the production build.
- Full image size is compile-time fixed: `104 / 8 * 212 = 2,756` bytes.
- Stream incoming bytes directly to the controller. Do not allocate a 2,756-byte framebuffer.
- Support uncompressed `CMD_DIRECT_WRITE_START`, `DATA` and `END` only.
- START initializes the controller and writes/generates any constant old plane without buffering
  the new image. DATA bounds-checks then sends bytes to SPI. END requires exactly 2,756 bytes,
  starts refresh, ACKs the END, then later notifies 0x73 success or 0x74 timeout.
- A compressed START is explicitly refused so current hosts fall back to uncompressed transfer.
- No auto-END in the first implementation. An explicit END keeps completion and error handling
  unambiguous.

### 5. Limited sharing is intentional and measurable

This target may include:

- the byte-for-byte canonical headers under `shared/protocol/`;
- header-only checked helpers such as `shared/core/od_span.h` where they save code and do not drag
  state;
- test-only use of shared config parsing to verify the static target blob.

It does not take `OD_SHARED_SOURCES`, `APP_SESSION`, `APP_XFER`, `HAL_RADIO`, `HAL_CRYPTO`, RXQ,
NFC, inflate, logging, config assembly/store, sensors, touch, buzzer or LED tiers. It also does not
create a pretend HAL surface merely to link capability-off implementations that cost more than the
target's entire useful RAM margin.

This is an exception to the existing “shared core owns the whole protocol stack” rule, not a
reversal for the other targets. `tools/check.sh` must name full-stack and slim targets separately;
do not weaken a ratchet with broad `grep -v nrf51` filters.

## Resource contract

Use S130 2.0.1 and the conservative memory map already demonstrated on LT213A:

| Region | Contract |
|---|---:|
| MBR + S130 Flash | `0x00000..0x1AFFF` (108 KiB) |
| Application Flash budget | `0x1B000..0x1F7FF` (18,432 B) |
| Reserved tail pages | `0x1F800..0x1FFFF` (2 × 1 KiB; untouched in MVP) |
| S130 RAM | `0x20000000..0x20001EFF` (7,936 B) |
| Application RAM | `0x20001F00..0x20003FFF` (8,448 B) |
| Heap | 0 B |
| Reserved stack | 2,048 B |
| Initial `.data + .bss` goal | <=5,888 B |
| Unallocated RAM margin goal | >=512 B after the reserved stack |

The linker script must assert the Flash/RAM origins and ends. The build must fail when the app
crosses 18,432 Flash bytes, when static RAM leaves less than the reserved stack plus margin, or when
constructors/heap support enter the image. The exact S130-required RAM base returned by
`sd_ble_enable()` is captured in Gate 0; if it is above `0x20001F00`, raise the origin and shrink the
application budget rather than overlapping the SoftDevice.

Initial static RAM allocations should be bounded approximately as follows; actual map symbols, not
this estimate, decide the gate:

| Owner | Budget/shape |
|---|---:|
| S130 Prepare/Execute record arena | 0 B preferred (`NOBUF+AUTH`); 336 B fallback (`BUF+AUTH`) only if Gate 0 requires it |
| Contiguous command scratch | 244 B; validated copy assembled from authorized Prepare records |
| Pending notification | 20 B + metadata |
| BLE event scratch | <=128 B; valid only with the selected per-record RW-authorize path and verified at Gate 0 |
| Transfer/panel state | <=128 B |
| RTC heartbeat/watchdog state | <=16 B |
| Advertisement/MSD and identity | <=64 B |
| Static config | Flash only; <=1,024 B target cap, expected 133 B |
| Framebuffer | 0 B |
| Config assembly/store | 0 B |
| Session/crypto/replay | 0 B |

Prefer fixed-width integers, no libc formatting, no logging in release, no float, no dynamic
allocation and no C++. Use `-ffunction-sections -fdata-sections`, LTO and linker garbage collection.
Debug builds may expose counters through a debugger-visible struct but must not add RTT to the
release image.

## Supported command matrix

The matrix is the scope boundary. Every row gets an exact host test; adding a command requires an
explicit plan revision and a new size measurement.

| Command | MVP disposition | Maximum response |
|---|---|---:|
| `0x0040 CONFIG_READ` | standard multi-notification read, <=20 B each | 20 B |
| `0x0043 FIRMWARE_VERSION` | plaintext fixed 8-char SHA + patch | 14 B |
| `0x0044 READ_MSD` | current 16-byte MSD record | 18 B |
| `0x0050 AUTHENTICATE` | `AUTH_STATUS_NOT_CONFIG`, never a challenge | 3 B |
| `0x0070 DIRECT_WRITE_START` | uncompressed full-frame only | 2 B |
| `0x0071 DIRECT_WRITE_DATA` | 1..242 data bytes, stream to panel | 2 B |
| `0x0072 DIRECT_WRITE_END` | accept 3/7-byte forms; full refresh; ACK then 0x73/0x74 | 2 B each |
| `0x000F`, `0x0041`, `0x0042`, `0x0045`, `0x0051`-`0x0053`, `0x0073`, `0x0075`-`0x0077`, `0x0080`-`0x0083` | recognized unsupported response where the canonical contract defines one; no state mutation | <=8 B |
| unknown opcode | silent reject and no activity extension | 0 B |

The target maximum frame is the contract-aligned `PIPE_MAX_FRAME` ceiling of 244 bytes, even though
the current host's largest plain-BLE DATA frame is 232 bytes. The extra command capacity costs 12
static bytes. If Gate 0 selects buffered queued writes, its 336-byte arena is 16 bytes larger than
the equivalent 232-byte arena, making the former comparison approximately 28 bytes in total.
Keeping 244 avoids an ATT-layer rejection for a contract-legal frame. Reject any BLE value over
244 bytes before dispatch. Structural errors and unsupported commands must never start panel I/O.
Do not silently truncate a command, config response or image.

## Implementation sequence

Each numbered phase is independently reviewable and revertible. Do not combine the panel bring-up,
BLE transport and wire state machine in one commit.

### Phase 0 — feasibility and destructive-flash safety spike

1. Record the exact LT213A marking, nRF51822 package/RAM variant, board revision, panel markings,
   original advertisement, GATT table, connection interval and ATT MTU.
2. Before erasing a tag, dump and hash the complete code Flash, UICR, FICR-readable identity and
   RAM-independent calibration/config areas. Store private device dumps outside Git; commit only a
   redacted manifest with address ranges, hashes and recovery instructions.
3. Verify SWD pinout and that the original image can be restored on one sacrificial tag.
4. Build and flash a minimal C program against S130 2.0.1. Capture the `sd_ble_enable()` RAM base,
   final linker map and measured idle/current behaviour.
5. Create a temporary GATT characteristic with Write Request + Notify. From Linux/Bleak, macOS and
   the browser client if those are release requirements, send lengths 1, 20, 21, 230, 231, 232,
   233, 242, 243, 244 and 245. Confirm 21..244 arrive through contiguous Prepare/Execute records and
   245 is refused.
6. Exercise cancel, missing offset, repeated offset, mixed handle, execute-without-prepare,
   disconnect mid-write and CCC disabled. Confirm no partial command reaches the application.
7. At the pinned `../Firmware_NRF` commit, inventory the exact non-`S112` source/include set and
   diff its S130 initialization, GATT service, notification and panel-adjacent paths against the
   pinned LT213A implementation. Add a short provenance/decision record for each new target source:
   donor and commit, behaviour retained, behaviour rejected and the test that decides it.
8. Measure the encoded size returned by `sd_ble_evt_get()` for immediate, Prepare, Execute, cancel
   and `BLE_EVT_TX_COMPLETE` events. Prove that the selected 128-byte event buffer is large enough
   for the per-record authorize path; increase the declared buffer and RAM accounting if it is not.
9. Exercise both documented S130 queued-write MSCs on hardware. First reply to
   `BLE_EVT_USER_MEM_REQUEST` with `NULL` and prove `NOBUF+AUTH` still delivers every Prepare value
   through `BLE_GATTS_EVT_RW_AUTHORIZE_REQUEST`, followed by execute/cancel, while the application
   scratch reconstructs 244 bytes exactly. Then exercise `BUF+AUTH` with a 336-byte arena and
   capture request/release ordering. Prefer NOBUF only if all required clients and negative cases
   pass; otherwise select the measured buffered fallback. A NULL user-memory reply selects NOBUF
   mode—it is never counted as a refusal. Only the authorize status accepts or rejects a write.
10. Prove RTC1 is available alongside S130, can wake the main loop at a ten-second cadence from the
    SoftDevice idle call, and adds acceptable measured idle current. This is required before
    selecting watchdog RUN-in-sleep in Phase 2.

**Gate 0:** original firmware is recoverable; the exact memory reservation is known; a 244-byte
reliable write works on required clients; NOBUF+AUTH or BUF+AUTH is selected from captured event
behaviour; the RTC heartbeat works; and one measured minimal image fits the map. If long writes
fail on a required client, stop and settle the 20-byte host-ceiling fallback before Phase 2.

### Phase 1 — reproducible freestanding build and release artifact

1. Add the target CMake/toolchain/linker skeleton. Build directly with GNU Arm Embedded and Nordic
   SDK/S130 headers; do not inherit the reference project's PlatformIO/Arduino build.
   Derive a minimal, explicit startup/SoftDevice source inventory from the SDK 12.3 material in
   `../Firmware_NRF`, then make the build consume separately configured SDK roots rather than the
   sibling checkout implicitly.
2. Pin supported SDK and S130 versions plus SHA-256 of the separately supplied S130 HEX. Do not
   redistribute the SoftDevice binary.
3. Produce application ELF/HEX/BIN, map, `size` report and JSON manifest. Optionally merge S130 +
   app into a full SWD image only when the locally supplied SoftDevice hash matches.
4. Add `check_image.py` to verify address ranges, no overlap, vector/reset address, stack/heap
   symbols, reserved pages and merged-HEX bytes.
5. Add the target to `build-release.sh --list` and release manifests, but mark it experimental
   until all hardware gates pass.

**Gate 1:** clean build from documented roots; deterministic application HEX; negative packaging
tests catch the wrong S130, overlap, oversize app and missing stack reservation.

### Phase 2 — S130 BLE transport with bounded backpressure

1. Implement the standard 0x2446 service and same-UUID command characteristic. One peripheral
   connection, open permissions, variable length, max attribute length 244, Write Request + Notify
   only. Set write authorization on the value attribute; do not compile the SDK QWR module.
2. Decide identity from Gate 0 evidence. Preserving the factory BLE address preserves
   Home Assistant/`py-opendisplay` device identity and existing automations, but requires an
   installer cache-clear step for the changed GATT table. Prefer that path if the client's
   `clear_cache()` plus documented OS steps work reliably. If stale caches make installation
   unreliable, use a stable alternate random-static address derived from FICR and explicitly warn
   that the flashed tag appears as a new device and automations must be migrated. Derive the GAP
   name from the selected stable identity; do not use a fleet-wide hard-coded identity.
3. Compile exactly the queued-write mode selected at Gate 0. Preferred `NOBUF+AUTH` supplies no
   arena and deliberately answers `BLE_EVT_USER_MEM_REQUEST` with `NULL`; Prepare data is copied
   from authorize events into the application scratch. Fallback `BUF+AUTH` supplies one 336-byte,
   four-byte-aligned arena: at ATT MTU 23, a 244-byte command needs at most 14 records, or 84 header
   bytes + 244 data bytes + a two-byte terminator = 330 bytes. Static-assert the fallback size and
   keep the fixed-MTU assumption adjacent to it. Do not compile both storage modes into release.
4. Use `BLE_GATTS_EVT_RW_AUTHORIZE_REQUEST` as the application ingress for every Prepare record.
   Require the command characteristic handle, monotonically contiguous offsets, a non-empty
   <=18-byte record and total <=244 before replying success; copy accepted bytes into the single
   244-byte command scratch. Execute-now dispatches only the completed scratch after authorization;
   cancel, rejection, unsubscribe and disconnect clear the application assembly state. The command
   scratch is an owned validated copy, not a view into the SoftDevice arena. Immediate <=20-byte
   Write Requests take the same authorization/validation path without waiting for Execute; their
   S130 authorize reply sets `update=1` and supplies the validated bytes as required for a normal
   Write Request.
5. This is new transport code: the immediate-write-only S130 branch in `../Firmware_NRF` is not a
   queued-write implementation. Use SDK 12.3's QWR source only as an event/API oracle, not as a
   linked dependency with its generic handle lists and callbacks.
6. Keep SoftDevice storage mode separate from command acceptance. A NULL reply to
   `BLE_EVT_USER_MEM_REQUEST` selects documented NOBUF+AUTH operation and does not reject a Prepare;
   only the later authorize status accepts or refuses it. In BUF+AUTH, lend the arena only when it
   is not already loaned, and treat `BLE_EVT_USER_MEM_RELEASE` as the sole event that returns
   ownership. Cancel, rejection, unsubscribe and disconnect may clear scratch/state immediately,
   but must not zero, parse or re-lend a buffered arena until RELEASE arrives. NOBUF+AUTH carries no
   arena ownership state.
7. Handle two mandatory S130 control events explicitly. On `BLE_GAP_EVT_SEC_PARAMS_REQUEST`, call
   `sd_ble_gap_sec_params_reply(..., BLE_GAP_SEC_STATUS_PAIRING_NOT_SUPP, NULL, NULL)` so an
   opportunistic pairing attempt is refused rather than left pending. On
   `BLE_GATTS_EVT_SYS_ATTR_MISSING`, call `sd_ble_gatts_sys_attr_set(conn, NULL, 0, 0)` so CCC
   writes and later `sd_ble_gatts_hvx()` calls work on first connection and reconnect without a
   bond database.
8. Pull BLE events in the superloop; do not run panel operations inside a SoftDevice callback.
9. Configure the watchdog to run during CPU sleep as well as active execution, giving a real
   30-second wall-clock bound. Start it before SoftDevice initialization so every initialization
   failure also has a reset path. Arm an RTC1 compare heartbeat at most every ten seconds as soon as
   the SoftDevice is ready so an otherwise idle `sd_app_evt_wait()` wakes the main loop in time to
   feed it. The nRF51 watchdog cannot be stopped after START; an initialization or heartbeat failure
   deliberately stops feeding and resets instead of sleeping forever. Feed it only after healthy
   main-loop progress or bounded panel polling, never from the RTC/BLE interrupt or callback. Test a
   lost wake source, a deliberate main-loop stall, long idle operation and a maximum-duration
   refresh; record the heartbeat's measured current cost.
10. Use one 20-byte egress slot. Advance it only after `sd_ble_gatts_hvx()` accepts the notification;
   on S130 2.0.1 retain it on `BLE_ERROR_NO_TX_PACKETS` and retry after `BLE_EVT_TX_COMPLETE`. A
   response producer owns command admission until its final notification has been accepted by the
   SoftDevice. `CONFIG_READ` continuation chunks belong to that same producer; they are not second
   commands. END retains ownership across its ACK, panel refresh and final 0x73/0x74 notification.
11. While a producer owns admission, reject every new command at write authorization with a named
   target-local ATT application-busy status based at `BLE_GATT_STATUS_ATTERR_APP_BEGIN`. Do this
   before copying or mutating protocol state. Do not disconnect the peer and do not retain a
   deferred command buffer. `py-opendisplay` wraps this status as a generic `BLEConnectionError`,
   indistinguishable at its public API from other write failures, and therefore has no automatic
   busy retry. The underlying link must remain connected and become usable when the producer ends;
   pin that host-visible outcome rather than claiming structured busy semantics.
12. Require CCC subscription before accepting application commands. Clear RX/TX/transfer state on
   unsubscribe and disconnect. An unexpected `BLE_GATTS_OP_WRITE_CMD` is never dispatched; the
   characteristic does not advertise Write Without Response and write authorization does not cover
   commands.
13. Set conservative connection parameters first. Throughput tuning comes only after functional and
   current measurements; do not spend RAM on larger queues speculatively.

**Gate 2:** host transport tests plus hardware capture prove 20-byte notification ceiling, exact
long-write reconstruction, no response loss under `BLE_ERROR_NO_TX_PACKETS`/`BLE_EVT_TX_COMPLETE`,
working notifications on first connect and reconnect after `BLE_GATTS_EVT_SYS_ATTR_MISSING`, prompt
pairing refusal, and the Gate-0-selected queued-write mode: NOBUF delivers authorized records with
zero arena, or BUF preserves ownership through `BLE_EVT_USER_MEM_RELEASE`. Busy admission leaves the
link connected while the reference host reports a generic write error. Long idle operation does not
reset, but a lost heartbeat wake or deliberate main-loop stall resets within the watchdog bound.

### Phase 3 — read-only identity and capability path

1. Generate the static config blob and validate it in a host test with the canonical structs and
   shared parser. Static-assert every wire struct size used by the generator and the final blob's
   `OD_NRF51_STATIC_CONFIG_MAX_SIZE` limit of 1,024 bytes.
2. Implement `CONFIG_READ` as a producer, not a burst: emit one <=20-byte frame, wait for egress
   capacity, then advance. Chunk 0 includes total length once; later chunks carry only chunk number
   and data as the canonical contract requires.
3. Implement short `FIRMWARE_VERSION`, `READ_MSD` and `AUTHENTICATE/NOT_CONFIG` responses.
4. Build the 16-byte MSD without float formatting or heap. Keep encryption and unsupported
   capability bits clear, keep the 11-byte dynamic sensor region zero when no sensors are declared,
   clear the reboot bit after the first connection and advance the main-loop nibble. The wire format
   has no unavailable battery sentinel: report the literal 0.00 V value until the nRF51 VDD ADC
   conversion is hardware-qualified, and document that limitation rather than calling zero unknown.
5. Implement every unsupported-command disposition in one table-driven switch so the supported
   matrix and response sizes are auditable.

**Gate 3:** unmodified `py-opendisplay` auto-interrogates the device; the reconstructed config is
byte-identical and <=1,024 B; every notification is <=20 B; auth always returns NOT_CONFIG;
unsupported commands perform no panel/Flash/reset action.

### Phase 4 — LT213A full-refresh panel driver

1. Import only the hardware-verified monochrome OTP path from the pinned LT213A reference commit,
   preserving GPL attribution. Record the donor repository, exact commit, source files and retained
   licence in a `Provenance` section of `targets/nrf51-s130/README.md` and use an accurate SPDX
   identifier in imported source; there is no repository-root `THIRD_PARTY.md`.
2. Fix the board map at compile time: MOSI P0.30, SCK P0.0, CS P0.1, DC P0.2, RESET P0.3,
   BUSY P0.4, BS P0.5. SPI mode 0, MSB first. Do not add a generic GPIO/panel abstraction in MVP.
3. Expose a tiny begin/write/refresh/poll/abort interface. Every fallible operation has one cleanup
   path that powers down the controller and deasserts pins.
4. Generate the constant old plane directly or from a small repeated block; never materialize it.
5. Bound BUSY polling and total refresh time. Feed the watchdog while waiting. A timeout invokes
   abort/power-down and produces 0x74 only after egress is available. This uses the watchdog
   configuration established in Phase 2; panel timeout and watchdog timeout remain separate
   mechanisms.
6. Keep four-gray, partial update, recovered 2-bpp experiments and any standalone panel-status
   feature out of the production source list. UC81xx Get Status command `0x71` remains required for
   bounded BUSY polling in the retained OTP/full-refresh sequence. Similar 2.13-inch glass is not
   automatically supported.
7. During import, avoid the legacy names scanned by `tools/check.sh`'s shared-color ownership
   ratchet (`getBitsPerPixel`, `getplane` and `opendisplay_color_*`). The fixed monochrome driver
   does not need those abstractions. Run the ratchet immediately after the import rather than
   discovering the collision in Phase 6.

**Gate 4:** host byte-trace matches the selected reference flow; on hardware, a fixed 2,756-byte
test image has correct orientation/polarity, BUSY timing is captured, and abort leaves measured
panel power low. The longest successful measured refresh feeds the watchdog and does not reset;
a deliberately stalled main loop does.

### Phase 5 — slim DIRECT_WRITE state machine

1. States: `IDLE`, `RECEIVING`, `REFRESHING`, `REPORT_PENDING`. Keep counters and deadlines in one
   small struct; no hidden singleton per module.
2. START requires empty egress. In accordance with the canonical framing contract, a new valid
   START aborts any active direct transfer and begins a fresh one. Refuse compression/trailing
   unsupported shapes before calling the panel.
3. DATA is accepted only while RECEIVING, with a 1..242-byte body and
   `received + len <= 2756`. Write to the panel first; only then increment the count and queue ACK.
4. END accepts exactly the canonical 3-byte `[00][72][refresh]` form or 7-byte form with optional
   four-byte big-endian `new_etag`. Accept defined refresh values FULL (0) and FAST/PARTIAL (1), but
   perform the same full LT213A refresh for either because this profile exposes no partial mode.
   Parse and ignore the optional etag: this profile neither advertises nor persists partial/etag
   state. Reject every other length or refresh value without refreshing.
5. END succeeds only at exactly 2,756 received image bytes. Queue END ACK before starting/reporting
   completion in the order expected by `py-opendisplay`. Do not allow a fast panel completion to
   overtake the ACK.
6. Timeout, overflow, duplicate START restart, END-short, DATA-outside-transfer, panel failure, CCC
   loss and disconnect all use the same idempotent abort primitive. Explicitly include zero-length
   DATA, an overrun boundary test that ends exactly at 2,756 bytes, a DATA frame that crosses it,
   END from IDLE and a fast completion that could overtake the END ACK. Never refresh partial data.
7. `REFRESHING` and `REPORT_PENDING` retain the response-producer admission lock established in
   Phase 2. A read-only discovery command in that window receives the target-local ATT busy error;
   it is neither deferred nor answered out of order, and the connection remains open. The same
   policy applies between `CONFIG_READ` chunks. The reference host exposes that overlap as a
   generic `BLEConnectionError`, not a parsed protocol NACK or a retryable busy result.

**Gate 5:** host fault tests cover every state/event pair; sanitizer and fuzz runs find no
out-of-bounds access; hardware raw upload refreshes once, and each negative case leaves the next
clean upload usable without reboot.

### Phase 6 — repository gates and explicit slim exception

1. Add `OD_FULL_STACK_TARGETS` and `OD_SLIM_TARGETS` target sets to `tools/check.sh`. Existing
   transfer/dispatch/core-reset absence ratchets continue to scan every full-stack target. Do not
   exempt the whole `targets/` tree or change their meaning.
2. Add slim-specific structural checks:
   - only the command matrix above appears in the target route table;
   - no crypto/session/auth-challenge, PIPE, partial, zlib, config-write/store, DFU, NFC, LAN,
     touch, sensor, buzzer or LED implementation symbols link;
   - GATT command attribute and command scratch are exactly 244 bytes, and no response buffer or
     notification exceeds 20 bytes;
   - exactly one Gate-0-selected queued-write mode links: NOBUF has no arena object, while BUF has
     one 336-byte arena and its release-ownership checks;
   - generated static configuration is <=1,024 bytes and no writable config buffer links;
   - no framebuffer-sized object, heap call, C++ source/runtime, Arduino or PlatformIO file exists;
   - canonical protocol headers are included before any SDK headers with overlapping names;
   - linker map satisfies the Flash/RAM/stack budgets.
3. Add `--nrf51`; make `--targets` include nRF51 along with ESP32, Nordic-Zephyr and Silabs. A
   missing SDK/SoftDevice is a skip and therefore exit 2, never a pass.
4. Add a target-composition corpus executable that drives the production `slim_protocol.c`, not a
   fake shared dispatcher. This requires refactoring `tests/host/corpus_runner.c` to inject a
   dispatch-entry seam: existing full-stack profiles keep calling `od_dispatch_frame()`, while the
   slim executable calls its production route entry. It is not merely another
   `od_corpus_profile_caps()` value. Tag applicable vectors explicitly and add vectors for MTU 23,
   unsupported auth, small config chunks and all transfer failures.
5. Add unit/fuzz targets for ATT long-write reconstruction, egress backpressure, config producer,

   fake S130/panel seams.
6. Preserve `build-release.sh`'s existing run-all-targets-after-failure behaviour. Add only the new
   nRF51 size and SoftDevice-hash fields to its target and top-level manifests, with a regression
   test showing that an nRF51 failure still does not suppress later targets.
7. Amend `CLAUDE.md` when the target lands. Decision 8 must distinguish the maintained

   must name the nRF51 target-side slim protocol/transfer implementation as an explicit exception
   to “no promoted subsystem has a target-side reimplementation.” Keep the exception target-specific
   rather than weakening the rule for existing targets. Decision 12 remains unchanged because this
   target does not override `OD_CONFIG_MAX_SIZE` or compile its ABI-sensitive assembler struct; the
   1 KiB immutable-blob limit is target-local.
   Decision 3 becomes four toolchains — ESP-IDF, west/Zephyr, SLC and Nordic SDK 12.3/S130 with
   bare GNU Arm, all CMake. What that decision protects is unchanged: unification is about shared
   *source*, not one build system, and a fifth toolchain still needs its own plan.
   Decision 4's grouping key is the SoftDevice-versus-Zephyr split, not silicon vendor. nRF52840
   stays a board on `nordic-zephyr`; nRF51822 cannot be one, because nRF Connect SDK dropped nRF51

### Phase 7 — client integration and throughput/power characterization

1. Run the live `../py-opendisplay` client against a fake production protocol and real hardware:
   connect, auto-interrogate, prepare a 104 × 212 monochrome image, uncompressed upload, END ACK and
   refresh status.
2. Test Linux/BlueZ, macOS CoreBluetooth and browser/Web Bluetooth if browser support is claimed.
   Record which stacks actually generate Prepare/Execute for >20-byte Write Requests. Include iOS
   and Android if claimed, force an opportunistic pairing request, and verify explicit refusal does
   not stall the connection. Reconnect after clearing CCC/system attributes and prove notifications
   resume.
3. Measure transfer time, ATT transaction count, connection interval, radio current, panel current,
   idle connected current and advertising current. The first goal is correctness within budget,
   not parity with nRF52 throughput.
4. Only after measurement, tune connection interval and slave latency. Keep stop-and-wait ACKs;
   do not add PIPE/reorder slots unless a later plan shows a user-visible need and measured RAM.
5. Test at least 100 consecutive uploads plus forced disconnect at every transfer boundary. Track
   stack high-water by canary or debugger sampling; static stack analysis alone is not a runtime
   measurement.

**Gate 7:** all claimed clients work without a private adapter; 100-upload soak has no reset,
wedged panel or stale state; measured stack margin is >=512 B; current and transfer time are
recorded as facts, not estimates.

## Deferred features — each needs a separate plan

- Authentication/encryption. It is explicitly unsupported, not merely postponed behind a macro.
- Writable/persistent configuration.
- Compression. A 512-byte inflate window may be feasible, but Flash and measured stack decide.
- PIPE/sliding-window transfer. MTU-20 slots are small, but its protocol and response-reservation
  complexity is not free.
- Partial and four-gray refresh. The linked experiment reports unresolved image-quality issues.
- OTA/DFU or a bootloader. The 128 KiB part has no room assumption for it here.
- Generic nRF51822 boards or other 2.13-inch panels.
- Timer-wake System OFF, LEDs, buttons, sensors, NFC, buzzer, logging and diagnostics.

## Completion definition

This plan is complete only when all of the following are true:

- the freestanding S130 target builds without PlatformIO/Arduino and fits the enforced map;
- `OD_NRF51_STATIC_CONFIG_MAX_SIZE` is 1,024 bytes, the generated immutable config fits it, no
  shared config ABI variant is created and no config-write buffer is linked;
- every supported response is <=20 bytes and every >20-byte request is reconstructed only after a
  successful contiguous Execute Write;
- pairing requests are explicitly refused, missing GATT system attributes are initialized, and the
  selected NOBUF+AUTH mode uses zero arena or the BUF+AUTH fallback does not reuse its arena before
  `BLE_EVT_USER_MEM_RELEASE`;
- competing commands receive ATT busy without disconnect while config or refresh responses own the
  producer, producer continuation notifications remain ordered, and the reference host's generic
  write-error result is pinned rather than described as structured busy;
- the image path uses zero framebuffer bytes and refreshes a real LT213A correctly;
- authentication always reports not configured and no crypto/key/replay symbol exists in the ELF;
- unmodified supported clients can interrogate and upload, or the plan is revised before claiming
  that compatibility;
- plain and full target gates pass without skips;
- hardware evidence, release manifest and documented non-features agree.

## Implementation record — 2026-09-06

The experimental target, slim production corpus profile and release/image gates are implemented on
`feat/nrf51822-slim`. GNU Arm Embedded 12.2.1 produced byte-identical clean HEX files in two build
