## 1. Behavioural comparison

### 1.1 Pattern model — identical on all three

Decode of the 12-byte `struct LedFlashPattern` (`shared/protocol/opendisplay_structs.h:1103-1115`)
out of `LedConfig.reserved[0..11]` (`:752`) is line-for-line the same:

| Field | ESP32 | Nordic | Silabs |
|---|---|---|---|
| `brightness = (byte0>>4)+1` | `device_control.cpp:371` | `opendisplay_led.c:157` | `opendisplay_led.c:206` |
| colours 1/2/3 = bytes 1,4,7 | `:372-374` | `:158-160` | `:207-209` |
| loop delay = high nibble of 2,5,8 | `:375-377` | `:161-163` | `:210-212` |
| loop count = low nibble of 2,5,8 | `:378-380` | `:164-166` | `:213-215` |
| inter-loop delay = bytes 3,6,9 | `:381-383` | `:167-169` | `:216-218` |
| `grouprepeats = byte10 + 1` | `:384` | `:170` | `:219` |
| mode = low nibble of byte 0; `!= 1` ⇒ stop | `:406-410`, `:554-560` | `:199-203`, `:360-363` | `:264-268`, `:447-451` |

The 11-phase enum is character-identical in all three
(`device_control.cpp:282-294`, `nordic .../opendisplay_led.c:24-36`,
`silabs .../opendisplay_led.c:20-32`), as is the runtime state struct
(`:296-321` / `:38-52` / `:34-58`) apart from ESP32's extra `delay_until_ms` field (`:320`).

The 8-level software-PWM slice order — thresholds 7,1,6,2,5,3,4 for R/G and 3,1,2 for B, one
100 µs slice each, `brightness` iterations — is byte-for-byte the same three times
(`device_control.cpp:661-691`, `nordic:88-114`, `silabs:134-162`). Nordic's comment at `:83-87`
explicitly names the ESP32 function as its reference.

**Shared quirk worth preserving exactly:** `grouprepeats = byte + 1`, so wire byte **254** yields
255 = the infinite sentinel, and wire byte **255** wraps to 0, which makes
`group_pos(0) >= grouprepeats(0)` true on the first pass and terminates the pattern immediately
while clearing mode. Same on all three (`:384`/`:419`, `:170`/`:210`, `:219`/`:277`). The nibble
packing is documented as OEPL-compatible (`opendisplay_structs.h:1100`) — do not "fix" either.

## 2. The live bug on `efr32bg22-slc`

**This is not the `a2313b5` bug being re-reported. That one was Nordic's, and it is fixed
(`opendisplay_led.c:22,236,267,293,302`). Silabs has never had the fix, because
`targets/efr32bg22-slc/opendisplay_led.c` is a byte-identical import of the pre-fix Silabs repo.**

`led_run_step()` (`targets/efr32bg22-slc/opendisplay_led.c:255-394`) returns only when it schedules
a delay. With every delay nibble/byte zero it never schedules one:

- `LED_PHASE_LOOP{1,2,3}` with `loopNdelay == 0` falls through with `break` (`:305,338,372`) and
  re-enters the `for(;;)` at `:270`.
- `LED_PHASE_LOOP3` exhausted with `ildelay3 == 0` does `group_pos++; phase = GROUP; break`
  (`:361-363`) — the group-closing edge that ESP32 (`device_control.cpp:493-496`) and Nordic
  (`:289-294`) both turned into a yield.
- `LED_PHASE_GROUP` with `grouprepeats == 255` never terminates (`:277`).

So one accepted `CMD_LED_ACTIVATE` with `mode = 1`, `group_repeats = 254`, and all six delay
fields zero makes `led_run_step()` **never return**. The call chain is
`opendisplay_led_process()` (`:474`) ← `opendisplay_ble_process()` (`opendisplay_ble.c:2054`) ←
`app_process_action()` (`app.c:50`) ← the superloop (`main.c:67-79`). **BG22 has no watchdog** —
no `wdog` component appears in `opendisplay-bg22.slcp` or `cmake_gcc/opendisplay-bg22.cmake`, and
the target deliberately declines the `HAL_WDT` tier (`shared/sources.cmake`, CLAUDE.md § Status).
Result: permanent hang of BLE, the panel, advertising and NFC, recoverable only by power cycle.

A *finite* pattern with zero delays is only quantitatively better: 254 groups × 45 flashes ×
16 brightness × 700 µs ≈ **128 s** inside one superloop pass, which drops the BLE connection.

Reachability: `0x0073` goes through the shared gate — only `CMD_FIRMWARE_VERSION` and `0x0050` are
exempt (`shared/core/od_dispatch.c:201,215-224`) — so it needs a live session when encryption is
enabled. With security off (or a zero-key config) it is reachable by any connected client. BG22 has
never been flashed, so this has never bitten anyone.

**Two independent things follow, and they should not be conflated:** the promotion fixes this
permanently, and a six-line pre-fix on `codex/silabs-c13` fixes it now. §5 Q1.

## 3. The proposed seam

### 3.1 Portable policy → `shared/core/od_led.c` + `od_led.h`

Everything in §1.1 — pattern decode, the 11-phase machine, repeat accounting including both
`grouprepeats` edge cases, the `LED_DELAY_FACTOR_MS 100` scaling, the `LED_MIN_STEP_DELAY_MS 1`
floor, the software-PWM slice order and the invert-flag application, and the activate/stop
admission rules. That is roughly 420 lines replacing ~1,130 across three targets.

```c
/* shared/core/od_led.h */
#define OD_LED_IDLE  UINT32_MAX   /* nothing scheduled */

void     od_led_init(struct od_config *cfg);   /* configure all four channels, park off */
int      od_led_activate(uint8_t instance, od_span_t pattern);  /* 0 ok, 2 refused */
int      od_led_stop(uint8_t instance, bool instance_given);
uint32_t od_led_service(uint32_t now_ms);      /* ms until next step, or OD_LED_IDLE */
bool     od_led_active(void);

/* The flash primitive, exposed because ESP32's boot animation is a second caller
 * (display_service.cpp:924-927). Blocking, bounded: brightness x 7 x 100us. */
void     od_led_flash(const struct LedConfig *led, uint8_t color, uint8_t brightness);
void     od_led_all_off(const struct LedConfig *led);
```

`od_led_activate()` takes an `od_span_t` per decision 1's span rule; the existing three all take
`(const uint8_t *, uint16_t)`.

Two divergences get resolved by the promotion, both in the authority's favour (`../Firmware` per
CLAUDE.md § Migration constraints):

- **Deadline poll beats timer callback.** ESP32's wrap-safe `(int32_t)(now - due) < 0`
  (`device_control.cpp:529`) is the reference. The `k_timer` (`nordic:54-55`) and
  `sl_sleeptimer_timer_handle_t` (`silabs:60-61`) objects and both `volatile bool s_timer_due`
  flags — state written from callback context for no reason — are deleted. On BG22 that also
  reclaims a sleeptimer handle from a target with 480 B of headroom.
- **No implicit instance.** The runner drives the `struct LedConfig *` it holds. ESP32's
  `activeLedInstance` global (`device_control.cpp:405,641-651`) does not survive; the boot
  animation passes its `LedConfig *` to `od_led_flash()` explicitly. `ledFlashActive` and
  `ledFlashPosition` are deleted outright as write-only. This is the same correction C11 made for
  frame context, and the same ratchet shape applies.

### 3.2 Target driver — the exact HAL functions

Only four primitives are actually target-specific:

| Need | esp32-idf today | nordic-zephyr today | efr32bg22-slc today |
|---|---|---|---|
| write one channel | `od_hal_gpio_write(cfg, bool)` (`hal/od_hal_gpio.h`) | `od_gpio_write(cfg, bool)` (`src/od_gpio.h`, impl `od_gpio.c:146-154`) | file-**static** `od_gpio_write()` (`opendisplay_led.c:91-103`) over `GPIO_PinOut{Set,Clear}` |
| configure a channel as output | `od_hal_gpio_config_output(cfg, bool)` | `od_gpio_configure_output(cfg, bool)` | file-static `od_gpio_mode_push_pull()` (`:81-89`) + `CMU_ClockEnable` (`:400`) |
| sub-ms busy wait | `od_hal_delay_us(us)` (`hal/od_hal_time.h`) | `k_busy_wait()` (`:92`) | `sl_udelay_wait()` (`:138`) |
| monotonic ms | `od_hal_uptime_ms()` | `k_uptime_get_32()` | `sl_sleeptimer_tick_to_ms(sl_sleeptimer_get_tick_count())` (`opendisplay_ble.c:2055`) |

**`od_hal_gpio` exists but is not shared, and that is the whole gap.** There are three headers with
three names and the same contract: `targets/esp32-idf/hal/od_hal_gpio.h` and
`targets/nordic-zephyr/src/od_gpio.h` both take an *opaque target-encoded pin byte* decoded inside
the HAL, and both no-op on an undecodable byte (`od_gpio.c:151-153`;
`od_hal_gpio.h` documents the identical rule and names all three encodings). Silabs implements the
same contract privately at `opendisplay_led.c:63-79`.

**Recommendation: promote a two-function subset of `od_hal_gpio` and a two-function subset of
`od_hal_time` into `shared/hal/`. Do not invent an `od_hal_led`.**

```c
/* shared/hal/od_hal_gpio.h  -- minimal subset; esp32's header is the authority (decision 14) */
#define OD_PIN_UNUSED 0xFFu
void od_hal_gpio_config_output(uint8_t cfg, bool initial_high);
void od_hal_gpio_write(uint8_t cfg, bool level_high);

/* shared/hal/od_hal_time.h -- minimal subset */
uint32_t od_hal_uptime_ms(void);
void     od_hal_delay_us(uint32_t us);
```

An `od_hal_led` whose only operations are "write a pin" and "wait 100 µs" *is* `od_hal_gpio` with a
different name, and it would need a second implementation per target of a decoder every target
already has. Cost of the GPIO/time route: **zero** on ESP32 (the signatures and semantics are
already exactly these — a repoint, not a rewrite, which is what
`hal/od_hal_time.h:5-9` says it was written for), four forwarders on Nordic, and one small
`od_hal_gpio.c` on Silabs promoting `opendisplay_led.c:63-103` out of file scope.

The rest stays target-side: `CMU_ClockEnable(cmuClock_GPIO)` (`silabs:400`), the pin-encoding
decoders, and whatever the target does with the returned deadline (§3.3).

### 3.3 The deadline return value — why it is not a HAL entry

`targets/efr32bg22-slc/main.c:77` calls `sl_power_manager_sleep()` at the bottom of every superloop
pass. A pure deadline poll gives the part **no reason to wake** when the next LED step is due, so an
LED delay would stretch until some unrelated interrupt happened to fire. That is the one real
argument for BG22's `sl_sleeptimer`.

`od_led_service()` returning "ms until my next step" answers it without a HAL and without a second
vtable (decision 2):

- **esp32-idf** ignores the value. `loop()` already runs at ~1 ms (`main.cpp:1004`).
- **efr32bg22-slc** arms one `sl_sleeptimer` / power-manager requirement from it. The timer object
  moves to the target, where the reason for it lives.
- **nordic-zephyr** ignores it while connected (10 ms loop, `main.c:72`) and — this is a free fix —
  uses it to shorten `idle_delay_ms`'s 1000 ms chunk (`main.c:17,29`), so a pattern still running
  after a disconnect steps at its configured rate instead of once per second.

The alternative, an `od_hal_led_wake_at()`, would force a timer object onto ESP32, which needs none.
Decision 9.

### 3.4 What is deliberately *not* promoted

- `led_type` (`opendisplay_structs.h:727-732`: RGB / SINGLE / RY / FOUR_SEPARATE). Nothing honours
  it in the runner today, and ESP32's two filters disagree with each other (`led_type == 1` at
  `device_control.cpp:644`, `led_type == 0` at `display_service.cpp:922`). Promoting the current
  behaviour means promoting "ignored". Settle it as a follow-up (§5 Q5), not inside the swap.
- Hardware PWM / LED-driver-IC support. No target has any: all three drive plain GPIO with the same
  software PWM. Building an abstraction for it now is speculative generality. If one arrives, the
  overridable point is `od_led_flash()` behind an `#if`, not the pattern machine and not a vtable.
- ESP32's boot animation (`display_service.cpp:920-931`) — target policy, and it stays a caller of
  `od_led_flash()`.

### 3.5 `shared/sources.cmake` tier

A new tier. The tiers answer exactly one question — "what must a consumer already have to link
this?" — and `od_led.c` needs two HALs neither of which is a tier today:

```cmake
# HAL_IO needs shared/hal/od_hal_gpio.h AND shared/hal/od_hal_time.h implemented
# (write + config_output; uptime_ms + delay_us).
set(OD_SHARED_SOURCES_HAL_IO
    "${CMAKE_CURRENT_LIST_DIR}/core/od_led.c"
)
```

added to the `OD_SHARED_SOURCES` aggregate alongside the existing seven. **All three targets take
it** — esp32-idf via the aggregate, nordic-zephyr and efr32bg22-slc by adding `HAL_IO` to their
lists. Naming it `HAL_IO` rather than `HAL_GPIO` is deliberate: two HALs in one linkage statement
slightly bends the current 1:1 tier↔HAL reading, and the tier will not stay a single-source tier —
the buzzer runner is the obvious next tenant, and `targets/esp32-idf/src/buzzer_control.cpp:121`
says outright it was modelled on `s_led`/`processLedFlash`. Splitting into `HAL_GPIO` + `HAL_TIME`
is the alternative and would leave `od_led.c` needing to belong to two tiers, which the file's own
"every source belongs to exactly one tier" rule forbids.

## 4. Cooperative-execution contract

All three run this from a loop that also services BLE, the panel and the watchdog. The shared
runner must promise, and the header must state:

1. **Never sleeps, never blocks on a configured delay.** Loop and inter-loop delays are *scheduled*
   and the function returns. The only permitted blocking is inside one `od_led_flash()`.
2. **Bounded work per call: at most one flash.** ≤ `brightness × 7 × 100 µs` = **11.2 ms** at the
   maximum brightness of 16, plus O(1) phase transitions. Two flashes in one call is a contract
   violation — which is precisely what `LED_MIN_STEP_DELAY_MS` enforces on ESP32
   (`device_control.cpp:446,474,504`) and Nordic (`:236,267,302`), and precisely what Silabs lacks.
3. **Terminating regardless of pattern content.** A call returns after a bounded number of phase
   transitions even when every loop count and every delay is zero. The group-closing edge must
   yield (`device_control.cpp:493-496`, `nordic:289-294`) — that edge is the *only* yield when no
   flash ever runs, and it is what makes `grouprepeats == 255` a supported feature rather than a
   hang.
4. **Cheap when idle.** `od_led_service()` on an inactive runner is a predicate and a return
   (`:525`, `:391`, `:476` already).
5. **Not re-entrant, and not called from a command handler.** `activate` runs one step
   synchronously (`:569`, `:368`, `:458`), inside the dispatcher — so promise 2's 11.2 ms is also
   the worst-case latency `0x0073` adds to the dispatch path. Callers must not invoke
   `od_led_service()` from a hook. (ESP32's `idleDelay()` does call it at `main.cpp:1026`, and
   `main.cpp:1024-1025` already states the rule: `idleDelay` is called only from `loop()`.)

**Watchdog feed sites.** The contract is what protects them; they are not what protects the
contract:

- **esp32-idf** — `od_watchdog_app_service()` is the *first* statement of `loop()`
  (`main.cpp:865`), `processLedFlash()` the third (`:867`). A runner that did not return would
  starve the feed and trip the TWDT (widened to `OD_WDT_TIMEOUT_S` = 300 s while armed, per
  CLAUDE.md), i.e. a reboot loop rather than a clean failure.
- **nordic-zephyr** — feeds at `main.c:59` and inside `idle_delay_ms` at `:27`, in both cases
  immediately before `opendisplay_ble_process()` → `opendisplay_led_process()`
  (`opendisplay_ble.c:1062`). Same shape; a wedged runner is caught. Note the comment at
  `nordic .../opendisplay_led.c:17-22` — "this target has no watchdog" — **is now stale**, since
  `od_hal_wdt` landed on this target. The reasoning it supports is still right; the parenthetical
  is wrong. Fix it when the file goes.
- **efr32bg22-slc** — **no watchdog exists.** The contract is the only thing between a malformed
  LED command and a permanent hang (§2). This is also the argument for the promotion order: the
  shared runner must satisfy the *weakest* host, and BG22 is a superloop with no supervisor.

Bounding by wall-clock rather than by flash count is the tempting alternative and it is worse: it
makes step timing depend on the caller's service rate, which differs by three orders of magnitude
across the three targets (1 ms / 10 ms / event-driven).

## 5. Open questions, ranked

1. **Does the Silabs hang get a standalone fix now, or does it wait for the promotion?** It is a
   remotely-triggerable permanent hang on a watchdog-less part (§2). The minimal fix is six lines
   mirroring `a2313b5` into `targets/efr32bg22-slc/opendisplay_led.c:305,338,361-363,372`. Argument
   for now: BG22 hardware Gate 2 is imminent and this is exactly the class of thing a bench session
   trips over. Argument for waiting: the file is a byte-identical import, and diverging it from
   `../Firmware_Silabs/opendisplay_led.c` costs the free `diff` that just proved it undrifted. My
   read is fix it now and record the divergence — CLAUDE.md forbids deleting from the source repos,
   not fixing here first.
2. **Deadline poll, or keep a timer?** §3.1 proposes the ESP32 poll shape (the authority) plus a
   returned deadline (§3.3). **Unverified:** that `sl_power_manager_sleep()` with no armed
   sleeptimer really does leave the BG22 asleep past an LED deadline. If some other periodic wake
   (the BLE advertising interval, `OD_MSD_UPDATE_INTERVAL_MS` at `opendisplay_ble.c:2065`) already
   guarantees a wake at or below 100 ms, the returned deadline becomes an optimisation rather than a
   correctness requirement. Measure before designing around it.
3. **Promote `od_hal_gpio` + `od_hal_time` subsets, or scope an `od_hal_led`?** §3.2 argues for the
   subsets. The counter-argument is blast radius: promoting `od_hal_gpio` invites buttons, touch and
   the buzzer to follow, and the ESP32 header (`hal/od_hal_gpio.h:104-110`) already flags an
   unresolved problem — `od_hal_gpio_irq_lock()` is per-core on ESP32 and `shared/core` has no
   global-disable primitive. Promoting only `config_output` + `write` sidesteps that entirely, and
   should be stated as a hard scope boundary if this route is taken.
4. **Where does pin configuration live?** ESP32 configures LED pins in `display_service.cpp:905-919`
   during `initio`; Nordic and Silabs do it in `opendisplay_led_init()`. Does `od_led_init()` own it
   — and does it configure `led_4`, which two targets configure and none drives?
5. **Should the runner honour `led_type`?** Today nobody does, and ESP32's two filters disagree
   (`device_control.cpp:644` vs `display_service.cpp:922`). Answering "ignored, deliberately" is a
   fine answer, but it should be written down rather than inherited.
6. **Should stopping the LED be part of a shared sleep-quiesce?** ESP32 calls `ledStopForSleep()`
   (`main.cpp:1157`); Nordic and Silabs stop nothing before hibernate/EM4
   (`opendisplay_ble.c:1086-1090`, `:2099-2105`). `od_core_reset()` is the existing shared-teardown
   precedent. **Unverified:** whether BG22 EM4 pin retention leaves a mid-flash channel driven.
7. **What is the host-test oracle?** No test exists anywhere. ESP32 and Nordic agree byte-for-byte,
   so a table-driven step test writes itself, but there is no captured hardware trace, so the test
   would pin *the current implementation* rather than observed behaviour. Given the runner drives
   nothing but three pins and a timer, that is probably enough — but say so explicitly rather than
   implying the corpus-style rigour of `dispatch.json`.
8. **Does the buzzer follow into `HAL_IO`?** `buzzer_control.cpp:121` says it was modelled on
   `s_led`. If yes, the tier name and its documented prerequisites should be written for two
   tenants, not one — and the two promotions probably share a design review.
